## P0 资金正确性（错了直接赔钱）

### G-01 生成类提交的幂等键 ✅ 0.1.63 已实现（`/api/media/images` 已接入）

**业务后果**：用户弱网超时后重试、或跨标签页提交，同一张图扣两次额度。
额度是本项目**唯一对外收费口径**（生图/生视频/封面/海报/智能体对话），重复扣费即客诉退款。

**原状**：
- 参考站 `platform-client.js` 用 `SHA-256(账号 + 路径 + 请求体)` 做幂等键，全局拦截 POST，
  重放先回查原任务状态，**终态才清缓存**；仅 `400/403/422/429` 清键（视为参数错误必失败）
- 我方 `clientRequestId` **只存在于规划文档**，`增强型智能家居AI-SaaS平台规划文档.md:349`
  仍是未勾选待办 `- [ ]`
- 后端只有**作业级**幂等（`canvas.service.ts:264` `status !== 'pending'` 直接返回），
  防的是同一 `jobId` 重复执行，**防不住两个不同 jobId**
- 单页连点已被 `loading={generating}` 拦住；未覆盖弱网重试、切走再回来重发、跨标签页

**已实现**：
- `MediaAsset` 加 `clientRequestId String? @unique`，
  migration `20261015150000_media_client_request_id`（可空，允许多个 NULL，不带键的老调用方行为不变）
- `generateImage` 在**所有扣费之前**按 `(tenantId, clientRequestId)` 查重，
  命中直接返回原产物并带 `deduped: true`。DB 唯一约束才是真防线，前端那层只为体验
- 前端策略是**失败保留键、成功清除**：超时时后端若有记录则取回，若无则真生成；
  业务失败（后端未建记录）复用同一个键也无害
- **0.1.65 推广到全部扣费入口**：
  - 生视频：复用 `MediaAsset.clientRequestId`，不新增字段
  - 方案生成：`PlanProject` 加同名字段，migration `20261015150000…` 之后的
    `20261015190000_plan_client_request_id`；**幂等查询排在 `generatePages` 之前**
    （放扣费之后虽然能少扣钱，但模型已经白调了一次）
  - 幂等键生成器提为 `apps/web/src/lib/request-id.ts` 共用模块
- **验收已过**：5 条 smoke 覆盖（生图 3 条 + 生视频 1 条 + 方案 1 条），335/335 全绿

**逐个入口核对后的覆盖现状**（不是估计）：

### G-18 局部重绘的校验与拒绝发生在扣额度之后 ✅ 0.1.63 已修

接 G-05 时顺带查出来的**确定性额度损失**，与 G-01 同源。

原顺序：API Key 校验 → **`consume` 扣额度** → mask 参数校验(400) → 通道能力校验(503) → 真出图。
于是用户在 MiniMax 通道上圈选局部重绘时，**额度先被扣掉，然后才收到"通道不支持"**。
而代码自己的注释（`:96`）写着「校验在扣费前…不白扣额度」——**代码违背了自己声明的意图**。

已把 mask 入参校验、通道能力校验、读原图三段整体提到 `consume` 之前，
用 `editInput` 把结果带过扣费线，真正调用仍在扣费之后。不改行为语义，只是不再为必然失败的请求扣钱。

## P1 核心业务缺失（客诉与收入直接相关）

### G-02 报价的附加费用区块 ✅ 0.1.66 已实现

**业务后果**：上门安装费、布线费、调试费这类**实际必收的钱现在无处可填**，
报价单只能填设备，等于让门店自己线下补差价——这是产品不可用级别的缺口。

**原状**：`grep 费用|安装费|服务费` 在我方报价页**零命中**，只有设备行。

**已实现**：
- 三种计费方式（固定金额 / 按百分比 / 不另收费）+ 5 个高频模板
- 百分比实时显示计费基数；CSV 与 Excel 导出都含费用块
- 费用不进返利计提（返点按进货额算）；毛利含费用
- 计算提为 `apps/web/src/lib/quoteFees.ts` 纯函数，界面与导出共用，避免算出两个数
- **实测 10 场景全通过**，含 `none` 忽略残留金额、小数百分比两个边界

**参考站形态**（`quote-workbench.js`）：
- 三种计费方式：固定金额 / 按百分比 / 不另收费（金额置 0 且禁用）
- 5 个常用模板（`quote-workbench.js:8`）：系统对接服务费用、运输费、上门安装费 ¥200、
  综合布线费 ¥500、系统调试费 ¥300
- 百分比基数**排除赠品与服务费用类商品**（`quote-fees.js:17`）——避免二次计费
- 上限 50 项 / 名称 ≤80 字 / 非负且 ≤2 位小数 / percent ≤100（`quote-fees.js:22-27`）
- 实时预览"计费基数 ¥X"（`quote-workbench.js:1326`）

**验收**：能加费用项、百分比档基数正确排除赠品、导出报价单含费用合计。

### G-03 报价 `per_order` 按单服务口径 ✅ 0.1.66 已实现

**业务后果**：无法表达"这一项就是本单的服务总价"，只能拆成单价×数量，
导致重复计费（参考站专门为此做了与 6 个捆绑服务名的互斥，`quote-workbench.js:9-14`）。

**参考站规则**：数量恒 1、单价即本单总价、禁赠送/替换/调零、与分项费用互斥。

**已实现**：`Product.pricingMode`（`per_unit` 默认 / `per_order`）+ migration
`20261015200000_product_pricing_mode`；报价页数量列对 `per_order` 显示「本单总价」标签
而非输入框；重复点击不再累加数量；产品编辑页有对应下拉。
旧数据与不传该字段一律兜底 `per_unit`。

**未做**（参考站有、我方按 YAGNI 略过）：赠送行、替换产品、强制正金额校验、
与分项费用的名称互斥表。这些是围绕"赠品"展开的，而我方报价页**根本没有赠品概念**
（`grep 赠品` 零命中），照抄要连带造一整套赠品功能。

### G-04 任务状态机补「结果不确定」态 ✅ 0.1.66 已实现（未照抄 9 态）

**业务后果**：`unknown`（供应商结果未确认）与 `partial`（部分完成）
是**客诉高发区**——用户看到"生成中"转了很久，既不知道成功也不知道失败，
只能重试，于是又扣一次额度（与 G-01 叠加放大）。

**参考站三分组**（`task-center.js:4-6`）：
- 运行中：`queued` / `running` / `settlement_pending`
- 需关注：`unknown` / `partial` / `interrupted`
- 结束：`done` / `failed` / `canceled`

我方 `GenerationJob.status`（`schema.prisma:736`）只有 pending/running/done/failed，
前端再压成 running/failed/done 三色（`TaskBall.tsx:145`）。

**已实现（只补真实存在的两态）**：
- `unknown`：出图是「先扣额度再调模型」，扣费之后的失败不等于「没花钱的失败」。
  `markCharged` / `isChargedError` 打标记，`runJob` 据此记 `unknown` 而非 `failed`。
  `clearFinishedTasks` 只删 done/failed，**不误删待核对的**
- `interrupted`：出图 fire-and-forget，进程重启后作业永远停在 running，
  任务球一直转圈——这是「明明生成完却一直显示生成中」的根因。
  `onModuleInit` 启动时把超 30 分钟仍 pending/running 的标记为 interrupted
- 前端五类着色：`unknown` 用警示色区别于红色失败，文案直说该不该再点一次

**没有照抄的**：`partial`（对应批量生成，我方是单任务模型）、`settlement_pending`
（对应结算重试，我方无此流程）、`canceled`（无前端取消入口）。**定义了也不会出现，不做。**

## 纪律

1. **改任何影响界面的代码前先取证**（截图或 DOM computed style），改完重新比对
2. **子 agent 的审计结论必须自己复核再改**——本轮已有实例：逆向报告把报价 BigInt
   列为"资金正确性最高优先级"，实测我方最大误差 2.1e-13 元，属误报（audit §7.15）
3. **不照抄参考站的历史包袱**，只补真实业务缺口
4. 涉及钱的功能，验收标准是**实测数字**不是"看起来对"
