## 一、参考站的交付机制（逆向实证）

### 1.1 交付物是「三件套」，不是我方的一件

`app.js:3453` 明确列出三个文件：

```js
function p2DownloadLink(href, project) {
  var name = p2DownloadFilename(project);
  add(project.pptxPath, project.pptxUrl || href, '下载 PPTX', name);
  add(project.zipPath,  project.zipUrl,  '下载图片包', name.replace(/\.pptx$/i, '-图片包.zip'));
  add('deck-text.md',  project.deckTextUrl, '下载完整讲稿', name.replace(/\.pptx$/i, '-完整讲稿.md'));
}
```

**图片包 ZIP 是独立交付物**，我方完全没有。

### 1.2 打包发生在服务端，且绑校对状态

`app.js:3790`：

```js
async function packageP2() {
  var pkg = await api('/api/projects/' + op.id + '/package', {
    method: 'POST',
    body: JSON.stringify(p2ReviewBody())   // { contentReviewed, reviewedRevision, reviewedDigest }
  });
}
```

分享链接走同一道门（`app.js` `shareP2()` 也传 `p2ReviewBody()`）——
**校对没过，既不能打包也不能分享**。

### 1.3 校对是三重校验，不是单一开关

`app.js` `p2UpdateReview()`：

```js
var needed = state && (state.status !== 'confirmed'
          || state.reviewedRevision !== project.textRevision
          || state.reviewedDigest   !== project.deckDigest);
```

- 状态（confirmed）+ **版本号** + **内容摘要 digest** 三者都要匹配
- 任一不匹配，勾选框自动清空
- 未勾选时按钮 `disabled = true`，文案是「**校对后生成下载文件**」
- 服务端返回 `warnings[]`，按页展示：`第 X 页：<message>`

### 1.4 改任何一页 → 下载物立即失效

`app.js` `p2InvalidateDownload()`：

```js
delete project.pptxPath; delete project.zipPath;
delete project.pptxUrl;  delete project.zipUrl;
box.textContent = '页面已更新，下载文件待更新。请在交付阶段重新打包。';
```

即：**打包物是快照，不是实时渲染**。客户手上的文件永远对应一个确定版本。

### 1.5 文件名带版本与日期

```js
`${name}-${edition}-V${textRevision}-${date}.pptx`
// edition ∈ { A完整方案 | B售前提案 | 私宅设计提案 }
```

### 1.6 页数是素材驱动的，不是固定值

`app.js:3427`（本次补户型页的依据）：

```js
core + " 个沟通模块 + " + Math.max(0, floorplanCount - 1)
     + " 张额外户型图 + " + renderCount + " 个素材展示页 = 至少 " + materialMinimum + " 页"
```

实测界面文案（登录后所见）：

> 「10 个沟通模块 + 0 张额外户型图 + 0 个素材展示页 = 至少 10 页；
> 已选 10 页，预计实际 10 页；**初次出图约 ¥10.00**。」

页数选择器：`10 页 / 12 页 / 自定义`（`#p2PagePick`）。

## 三、结论

**界面设计（版式、配色、16:9 画布、留白）我方已达标**——
0.1.80/0.1.81 实测 10 页零溢出、底部留白 6%–13%、图片无留白。

**用户判断的「内容不够完整」是准确的**，缺口不在视觉，而在**交付链路**：

1. **PPTX 根本没导出成功**（#1）——这是最硬的伤，PPT 是用户点名要的产物
2. **图片包 ZIP 完全缺失**（#2）——参考站三件套里我方只有一件
3. **下载物与校对版本没有强绑定**（#5/#7/#8）——
   我方实时生成，改一个字后客户手上的旧文件仍然"合法"，
   参考站则会立即失效并要求重新打包

第 3 条是**正确性问题**，不是功能多少问题：门店校对完 V4，
发出去的 PPT 若对应的是 V3 内容，对客就是事故。
