### 1.6 页数核算公式（`app.js:3419-3434`）

- `floorplanCount` = 本地待传 + 已存

下限公式（app:3375-3379）：
```
residence-v1 : 8 + max(0, floorplanCount-1) + max(1, renderCount)
presales-v1  : 9 + max(0, floorplanCount-1) + renderCount
classic      : (!project || salesContentVersion===1) ? 10 + max(0, fp-1) + renderCount
                                                       : 3 + floorplanCount + renderCount
```

### 2.1 页字段体系（`plan2-workspace.js` — 本次补抓）

**固定 7 个字段名**（行 3）：
```
['页型','主标题','副标题','画面要点','汇报要点','视觉建议','客户感知价值']
```

**页解析 `pages(text)`**（行 5-9）：按 `^## (Slide N|第 N 页)` 切分；
无匹配时整篇作为第 1 页；标题剥离前缀。

**字段解析 `fields(raw)`**（行 10-17）：
- 匹配 `^([^\n#：:]{1,48})[：:]([^\n]*)`（键 1–48 字，不含换行/井号/冒号）
- 去掉列表符号（`- * + • ·`、数字序号）与 `**`/`__`/反引号
- **边界字段** = 上述 7 个 + `备注/来源/补充说明/内部备注`
- 若当前 active 是「画面要点/汇报要点」且下一行不是边界字段，则**不切分**（即要点可以多行）

还有 `patchField(text, number, key, value)`：按页号+字段名做**局部文本替换**，
不重写整篇——这是「保存单页字段不破坏其他内容」的关键。

## 三、第 3 步：生成与校对（出图 + 逐页精修）

### 3.1 出图队列（`app.js:159-188`）

- **前端无并发池**，单请求长轮询；并发与批量全在服务端
- 轮询 **360 次 × 10s ≈ 60 分钟**
- 仅 `502/503/504` 静默重试，其他业务错误立即抛
- 超时抛 `backgroundGenerationNotice`，**不自动重做**，提示查历史
- 进度：`setP2(38 + done/total*55, '已完成 X / Y 页…')`（app:4129）
- 渐进式预览：已出页显示图、未出页占位（app:3973-3976）

### 3.2 状态机

`project.status`（app:3635/3356/4107）：`created` / `images-ready` / `packaged`

`imageJob.status` 6 态（app:4117-4120 文案表）：
| 值 | 含义 |
|---|---|
| `done` | 全部完成（**前端合成**：slides 存在且 status∈[images-ready,packaged] 时） |
| `generating` | 页面正在生成 |
| `partial` | 部分失败，可仅补齐失败页 |
| `unknown` | 供应商结果未确认，需查询原任务 |
| `settlement_pending` | 图片已返回，正在恢复保存与结算 |
| `interrupted` | 原任务已中断，已完成页保留 |

`textTask.status`：`queued/running/publishing/unknown`（app:4138）

**卡住时强制查原任务**（app:4125）：status ∈ {unknown, settlement_pending, interrupted, generating}
且非 resume → 直接走 `resumeP2Pending()`，**禁止重新提交**。

## 十、PPTX 导出实测结论（0.1.82）

### 10.1 已确认正常的部分

导出链路**其实是通的**，实测证据（浏览器 console + 落盘文件）：

```
[pptx] 开始导出，原始页数 9
[pptx] 待取图 4 张
[pptx] 原图取齐
[pptx] 裁剪完成
[pptx] 写文件…
[pptx] 字节数 952535
[pptx] 已触发下载 汉江一品 3 栋 1802-标准方案-V4-2026-10-16.pptx
```

落盘产物：`952535 字节` / **10 张幻灯片** / **10 个媒体文件**
（10 = 9 文案页 + 1 户型页 ⇒ **户型图页已进入 PPTX**，与分享页页数一致）

### 10.2 三个曾被误判为「不生成」的坑

| 坑 | 真实情况 |
|---|---|
| `pptx.writeFile()` | Node 端 API，浏览器里静默什么都不写。已改 `write({outputType:'arraybuffer'})` |
| Office MIME | `application/vnd.openxmlformats-…` 在 Electron 内嵌浏览器会被判为不安全类型。已改 `application/octet-stream`（下载行为由后缀名决定，与 MIME 无关） |
| **`a.download` 文件名** | **宿主行为，非前端缺陷**：`<a>` 是否 appendChild 到 DOM 都试过，Electron 下载时仍以 `.com.minimax.agent.cn.XXXXXX` 随机名落盘。`a.download` 是标准行为，**在正常浏览器里没问题**，只在本宿主内失效 |

### 10.3 结论与正解

`a.download` 失效属**宿主限制**，改前端绕不过去。参考站的正解已经逆向到：

- 服务端打包 `POST /api/projects/{id}/package` → 返回 `pptxUrl`
- 前端 `GET /api/projects/{id}/file-link?path=` → 换**真实 HTTP 签名直链**
- 用普通 `<a href="签名直链" download>` 触发

指向真实 HTTP URL 的下载不受 `a.download` 限制，且顺带满足「下载物与校对版本绑定」的架构要求（见第七节批次 9）。

**因此批次 0 与批次 9 应合并实施**：不再修浏览器端 blob 下载，改为服务端打包 + 签名直链。

### 11.5 实测发现并修掉的一个体验缺陷

首版用 `<InputNumber min={9} max={20}>`，实测输入 25 时 **AntD 会静默拦掉并退回 9**
（`onChange` 根本不触发，用户看不到任何提示，也不知道被拦了）。
参考站用的是原生 `<input type=number>` + 自行 clamp，行为是**可见的**。

> 对「用户知道自己输入被改了」的场景就是错的，必须自己夹。

## 十二、批次 4 实施记录（0.1.84）：补充需求与服务资料

### 12.1 实现内容

对齐参考站 `P2_SALES_FIELDS`（`app.js:3540`）的 9 项，全部 `textarea rows=3 maxLength=2000`：

| 字段 | 含义 |
|---|---|
| `priorityNeeds` | 最重要的需求（按优先级） |
| `excludedItems` | 明确不做的项目 |
| `renovationStage` | 装修阶段 |
| `existingDevices` | 现有设备与生态 |
| `serviceEvidence` | 真实案例或交付依据 |
| `serviceScope` | 已确认服务范围 |
| `serviceContact` | 负责人与联系入口 |
| `budgetItems` | 已确认参考费用（每行 `项目\|类别\|区间`） |
| `budgetSource` | 费用来源与日期 |

- **落库**：schema 加 9 列（不用 JSON）。理由：这一组要进 LLM 提示词，
  也要能按「明确不做的项目」做交付前自检，散在 JSON 里查不动。
- **界面**：默认折叠（`<details>`）。九项全不填是常态，铺开占半屏反而挤掉要填的资料。
- **进入提示词**：`salesBriefLines()` 只输出填写过的，空项不占篇幅。

### 12.2 实测发现并修掉的一个语义缺陷

首版把 9 项统一写成「门店补充的事实（必须遵守，不要改写成推测）」，实测：

| 项 | 是否进入生成文案 |
|---|---|
| serviceContact（王工） | ✅ |
| renovationStage（水电） | ✅ |
| existingDevices（米家） | ✅ |
| **excludedItems（不做摄像头）** | ❌ **方案正文照样提了摄像头** |

根因：**「明确不做的项目」是约束，不是事实**。混在事实堆里，模型当成背景信息带过。

改为单独下发硬性约束：
```
硬性排除：方案正文、要点清单与讲解稿中都不得出现或推荐以下项目（客户已明确不做）：…
```
并补一条联动：填了 `budgetItems` 但没填 `budgetSource` 时，提示模型标明费用为参考。

### 12.3 修复后复测

| 项 | 结果 |
|---|---|
| 排除项「摄像头」出现次数 | **0** ✅ |
| 排除项「智能门锁」出现次数 | **0** ✅ |
| serviceContact / renovationStage / existingDevices | ✅ 均进入文案 |
| serviceEvidence | 未引用 —— **符合预期**，案例佐证是门店内部材料，强制写进客户方案会变成资料堆砌 |

> 原则：**约束类必须 100% 遵守，信息类不必全部引用**。
> 把 9 项一律强制进正文，方案会读起来像填表，反而降低可读性。

### 14.3 实测中抓到并修掉的两个问题

**① 服务端互斥校验写错了**
首版判「同房间出现两次就报错」，导致**同空间放多张图**这种正常情况被误杀

```
方案生成失败: Expected ',' or '}' after property value in JSON at position 2602 (line 77 column 56)
```

**没有任何重试**——门店只能反复手动重试。

> 这条缺陷的严重性高于任何功能缺失：它直接让用户「生成不出方案」。
> 教训：**对照实验**（拿一个不带新改动的请求复现）能立刻区分
> 「我引入的」和「本来就有的」，比读代码猜快得多。

## 十七、批次 0+9 实施记录（0.1.89）：交付三件套服务端打包

### 17.1 更正一个此前记错的前提

本节一开始写的是「搬上服务端的唯一理由是文件名：宿主对 blob 下载一律给随机名」。
**实测证明这个前提是错的**，需要更正：

- `~/Downloads` 里 2026-10-16 18:03 有一份 `汉江一品 3 栋 1802-完整讲稿.md` —— blob 下载的**文件名是保留的**
- 根因在 `lib/download.ts:14-17` 的注释里已经写明：
  **只有不把 `<a>` 挂进文档再点，才会丢文件名**，产物变成无名的 `.com.<bundleId>.XXXXXX`。
  那个修复早在本批次之前就做完了

也就是说，「blob 下载必然随机名」是**修复前的旧状态**，被我当成了现状记下来。
如果没在浏览器里真点一次、也没看一眼下载目录，这个错误前提会一直支撑着一个并不存在的理由。

所以服务端打包的真正价值是下面四条，与文件名无关：

1. **三件套合一** —— 参考站 `app.js:3453` 的交付形态，用户要的是一个 zip 而不是三个散文件
2. **图片包由服务端自动收集** —— 户型图、精装修、效果图的原图与空间分组信息都在服务端，
   让用户自己整理一遍既费事又容易漏
3. **校对闸门落到服务端** —— 前端弹框可以被绕过（直接调 API 就行），409 是真拦
4. **版本失效** —— 客户手里的旧链接不会悄悄指向新版本。blob 方案根本承载不了这条

文件名由服务端给定是顺带的正确做法（`Content-Disposition` + RFC 5987 编码），
但它不构成搬上服务端的理由。

### 17.2 职责边界（刻意不做多）

| 谁 | 做什么 | 为什么是它 |
|---|---|---|
| 前端 | 生成 PPTX（blob） | 依赖浏览器 canvas 做预裁剪与点位合成，搬到服务端要 node-canvas 原生编译 |
| 前端 | 传讲稿文本 | 纯字符串，本来就在前端 |
| 服务端 | 取图片包原图 | 原图都在 uploads 卷，让前端再传一遍纯浪费 |
| 服务端 | zip 打包 + 定文件名 + 签名直链 | 文件名与链接有效性只有服务端能给 |

`exportPlanPptx` 的返回值从 `void` 改成 `{ blob, fileName }`：
**产出而非直接下载**，单独下载的能力由调用方拿 blob 自己触发。

### 17.3 两个闸门（对应参考站的校对门与链接失效）

1. **打包前必须已逐页校对**，否则 409。
   我方判据沿用既有的 `reviewedRevision === versionNo`（改任意一页都会 bump 版本号并让校对失效），
   **不引入 `deckDigest`**：版本号已经能覆盖「改一个字」这个场景，再加一层摘要只是重复。
2. **下载时版本对不上直接 410**。客户手里的旧链接不能悄悄指向新版本 ——
   那等于让已经发出去的交付物被单方面改写。

### 17.4 踩到的一个坑：presigned 链接不能套用户 JWT 守卫

第一版给下载端点挂了 `JwtQueryGuard`（本以为「浏览器下载带不了 Authorization 头」就该用它），
结果 4 条断言全挂：

```
FAIL 签名直链下载成功且返回 zip
FAIL 文件名带中文方案名与版本号
FAIL 被改过的签名链接拿不到交付包（404）
FAIL 方案改版后旧交付链接失效（410）
```

根因：`JwtQueryGuard` 背后的 `JwtStrategy.validate` 要拿 payload 里的 `sub` **查库**
（`user.findUnique` + 比对 `tokenVersion`）。交付包链接是自签的，`sub='plan-package'`，
查不到用户 → `USER_NOT_FOUND` → 401。

正确语义是 **presigned URL：链接本身就是凭证**，靠 `JWT_SECRET` 签名防伪，
下载端不再查库、不再套 RBAC（生成链接时已经校验过 `content:generate`）。
能力清单里该端点声明为 `[]`，与无守卫的分享页一致。

> 教训：`JwtQueryGuard` 的适用面是「登录用户的资源」，
> 不是「任何需要 URL 直达的产物」。把二者混用会得到一个看似有鉴权、实则永远 401 的端点。

### 17.5 自己写的弱断言

同轮还发现一条自己写的坏断言：

```ts
check('下载到的是真 zip（PK 魔数）', (await dl.arrayBuffer()).byteLength > 0);
```

标签写着 PK 魔数，实际只判长度 > 0 —— **任何错误响应体都有长度**，
所以 4 个真实失败里有 1 个被误报成 PASS。改成真的比对 `buf[0]===0x50 && buf[1]===0x4b`。

断言的名字必须对应它实际检查的东西，否则下次排查时它会替你撒谎。
