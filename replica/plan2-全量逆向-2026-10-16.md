### 1.6 页数核算公式（`app.js:3419-3434`）

- `floorplanCount` = 本地待传 + 已存

下限公式（app:3375-3379）：
```
residence-v1 : 8 + max(0, floorplanCount-1) + max(1, renderCount)
presales-v1  : 9 + max(0, floorplanCount-1) + renderCount
classic      : (!project || salesContentVersion===1) ? 10 + max(0, fp-1) + renderCount
                                                       : 3 + floorplanCount + renderCount
```

### 2.1 页字段体系（`plan2-workspace.js` — 本次补抓）

**固定 7 个字段名**（行 3）：
```
['页型','主标题','副标题','画面要点','汇报要点','视觉建议','客户感知价值']
```

**页解析 `pages(text)`**（行 5-9）：按 `^## (Slide N|第 N 页)` 切分；
无匹配时整篇作为第 1 页；标题剥离前缀。

**字段解析 `fields(raw)`**（行 10-17）：
- 匹配 `^([^\n#：:]{1,48})[：:]([^\n]*)`（键 1–48 字，不含换行/井号/冒号）
- 去掉列表符号（`- * + • ·`、数字序号）与 `**`/`__`/反引号
- **边界字段** = 上述 7 个 + `备注/来源/补充说明/内部备注`
- 若当前 active 是「画面要点/汇报要点」且下一行不是边界字段，则**不切分**（即要点可以多行）

还有 `patchField(text, number, key, value)`：按页号+字段名做**局部文本替换**，
不重写整篇——这是「保存单页字段不破坏其他内容」的关键。

## 三、第 3 步：生成与校对（出图 + 逐页精修）

### 3.1 出图队列（`app.js:159-188`）

- **前端无并发池**，单请求长轮询；并发与批量全在服务端
- 轮询 **360 次 × 10s ≈ 60 分钟**
- 仅 `502/503/504` 静默重试，其他业务错误立即抛
- 超时抛 `backgroundGenerationNotice`，**不自动重做**，提示查历史
- 进度：`setP2(38 + done/total*55, '已完成 X / Y 页…')`（app:4129）
- 渐进式预览：已出页显示图、未出页占位（app:3973-3976）

### 3.2 状态机

`project.status`（app:3635/3356/4107）：`created` / `images-ready` / `packaged`

`imageJob.status` 6 态（app:4117-4120 文案表）：
| 值 | 含义 |
|---|---|
| `done` | 全部完成（**前端合成**：slides 存在且 status∈[images-ready,packaged] 时） |
| `generating` | 页面正在生成 |
| `partial` | 部分失败，可仅补齐失败页 |
| `unknown` | 供应商结果未确认，需查询原任务 |
| `settlement_pending` | 图片已返回，正在恢复保存与结算 |
| `interrupted` | 原任务已中断，已完成页保留 |

`textTask.status`：`queued/running/publishing/unknown`（app:4138）

**卡住时强制查原任务**（app:4125）：status ∈ {unknown, settlement_pending, interrupted, generating}
且非 resume → 直接走 `resumeP2Pending()`，**禁止重新提交**。

### 10.2 三个曾被误判为「不生成」的坑

| 坑 | 真实情况 |
|---|---|
| `pptx.writeFile()` | Node 端 API，浏览器里静默什么都不写。已改 `write({outputType:'arraybuffer'})` |
| Office MIME | `application/vnd.openxmlformats-…` 在 Electron 内嵌浏览器会被判为不安全类型。已改 `application/octet-stream`（下载行为由后缀名决定，与 MIME 无关） |
| **`a.download` 文件名** | ✅ **本条结论已被 0.1.89 实测推翻，原判定是错的**。当时记的是「无论是否 appendChild 到 DOM 都落成随机名」，实际只要 appendChild 就正常 —— 证据：`~/Downloads/2026-10-16` 有 `汉江一品 3 栋 1802-完整讲稿.md`（中文名完整）。真正的触发条件是**不挂进文档**。详见第十七节 17.1 |

### 10.3 结论与正解

> ⚠️ **本节前提已被推翻**（0.1.89 实测）：`a.download` 在本宿主里是**有效的**，
> 只要把 `<a>` appendChild 到文档再点。`lib/download.ts:14-17` 的注释就是这次修复的记录。
> 下面这条「服务端打包」的结论**方向仍然正确，但理由不是文件名**。

服务端打包的真正价值（0.1.89 落地并复盘）：
三件套合一、图片包由服务端自动收集、校对闸门落到服务端、旧链接随版本失效。
参考站的正解已经逆向到：

- 服务端打包 `POST /api/projects/{id}/package` → 返回 `pptxUrl`
- 前端 `GET /api/projects/{id}/file-link?path=` → 换**真实 HTTP 签名直链**
- 用普通 `<a href="签名直链" download>` 触发

指向真实 HTTP URL 的下载不受 `a.download` 限制，且顺带满足「下载物与校对版本绑定」的架构要求（见第七节批次 9）。

**因此批次 0 与批次 9 应合并实施**：不再修浏览器端 blob 下载，改为服务端打包 + 签名直链。

> ✅ **已实施（0.1.89）**：`POST /api/plans/:id/package` + `GET /api/plans/package/download?token=`，
> 见第十七节。其中 `deckDigest` 有意不做（版本号已覆盖），`warnings` 未做。

## 十二、批次 4 实施记录（0.1.84）：补充需求与服务资料

### 12.1 实现内容

对齐参考站 `P2_SALES_FIELDS`（`app.js:3540`）的 9 项，全部 `textarea rows=3 maxLength=2000`：

| 字段 | 含义 |
|---|---|
| `priorityNeeds` | 最重要的需求（按优先级） |
| `excludedItems` | 明确不做的项目 |
| `renovationStage` | 装修阶段 |
| `existingDevices` | 现有设备与生态 |
| `serviceEvidence` | 真实案例或交付依据 |
| `serviceScope` | 已确认服务范围 |
| `serviceContact` | 负责人与联系入口 |
| `budgetItems` | 已确认参考费用（每行 `项目\|类别\|区间`） |
| `budgetSource` | 费用来源与日期 |

- **落库**：schema 加 9 列（不用 JSON）。理由：这一组要进 LLM 提示词，
  也要能按「明确不做的项目」做交付前自检，散在 JSON 里查不动。
- **界面**：默认折叠（`<details>`）。九项全不填是常态，铺开占半屏反而挤掉要填的资料。
- **进入提示词**：`salesBriefLines()` 只输出填写过的，空项不占篇幅。

### 12.2 实测发现并修掉的一个语义缺陷

首版把 9 项统一写成「门店补充的事实（必须遵守，不要改写成推测）」，实测：

| 项 | 是否进入生成文案 |
|---|---|
| serviceContact（王工） | ✅ |
| renovationStage（水电） | ✅ |
| existingDevices（米家） | ✅ |
| **excludedItems（不做摄像头）** | ❌ **方案正文照样提了摄像头** |

根因：**「明确不做的项目」是约束，不是事实**。混在事实堆里，模型当成背景信息带过。

改为单独下发硬性约束：
```
硬性排除：方案正文、要点清单与讲解稿中都不得出现或推荐以下项目（客户已明确不做）：…
```
并补一条联动：填了 `budgetItems` 但没填 `budgetSource` 时，提示模型标明费用为参考。

### 12.3 修复后复测

| 项 | 结果 |
|---|---|
| 排除项「摄像头」出现次数 | **0** ✅ |
| 排除项「智能门锁」出现次数 | **0** ✅ |
| serviceContact / renovationStage / existingDevices | ✅ 均进入文案 |

> 原则：**约束类必须 100% 遵守，信息类不必全部引用**。
> 把 9 项一律强制进正文，方案会读起来像填表，反而降低可读性。

## 十七、批次 0+9 实施记录（0.1.89）：交付三件套服务端打包

### 17.1 更正一个此前记错的前提

本节一开始写的是「搬上服务端的唯一理由是文件名：宿主对 blob 下载一律给随机名」。
**实测证明这个前提是错的**，需要更正：

- `~/Downloads` 里 2026-10-16 18:03 有一份 `汉江一品 3 栋 1802-完整讲稿.md` —— blob 下载的**文件名是保留的**
- 根因在 `lib/download.ts:14-17` 的注释里已经写明：
  **只有不把 `<a>` 挂进文档再点，才会丢文件名**，产物变成无名的 `.com.<bundleId>.XXXXXX`。
  那个修复早在本批次之前就做完了

也就是说，「blob 下载必然随机名」是**修复前的旧状态**，被我当成了现状记下来。
如果没在浏览器里真点一次、也没看一眼下载目录，这个错误前提会一直支撑着一个并不存在的理由。

所以服务端打包的真正价值是下面四条，与文件名无关：

1. **三件套合一** —— 参考站 `app.js:3453` 的交付形态，用户要的是一个 zip 而不是三个散文件
2. **图片包由服务端自动收集** —— 户型图、精装修、效果图的原图与空间分组信息都在服务端，
   让用户自己整理一遍既费事又容易漏
3. **校对闸门落到服务端** —— 前端弹框可以被绕过（直接调 API 就行），409 是真拦
4. **版本失效** —— 客户手里的旧链接不会悄悄指向新版本。blob 方案根本承载不了这条

文件名由服务端给定是顺带的正确做法（`Content-Disposition` + RFC 5987 编码），
但它不构成搬上服务端的理由。

### 17.2 职责边界（刻意不做多）

| 谁 | 做什么 | 为什么是它 |
|---|---|---|
| 前端 | 生成 PPTX（blob） | 依赖浏览器 canvas 做预裁剪与点位合成，搬到服务端要 node-canvas 原生编译 |
| 前端 | 传讲稿文本 | 纯字符串，本来就在前端 |
| 服务端 | 取图片包原图 | 原图都在 uploads 卷，让前端再传一遍纯浪费 |
| 服务端 | zip 打包 + 定文件名 + 签名直链 | 文件名与链接有效性只有服务端能给 |

`exportPlanPptx` 的返回值从 `void` 改成 `{ blob, fileName }`：
**产出而非直接下载**，单独下载的能力由调用方拿 blob 自己触发。

### 17.3 两个闸门（对应参考站的校对门与链接失效）

1. **打包前必须已逐页校对**，否则 409。
   我方判据沿用既有的 `reviewedRevision === versionNo`（改任意一页都会 bump 版本号并让校对失效），
   **不引入 `deckDigest`**：版本号已经能覆盖「改一个字」这个场景，再加一层摘要只是重复。
2. **下载时版本对不上直接 410**。客户手里的旧链接不能悄悄指向新版本 ——
   那等于让已经发出去的交付物被单方面改写。

### 17.4 踩到的一个坑：presigned 链接不能套用户 JWT 守卫

第一版给下载端点挂了 `JwtQueryGuard`（本以为「浏览器下载带不了 Authorization 头」就该用它），
结果 4 条断言全挂：

```
FAIL 签名直链下载成功且返回 zip
FAIL 文件名带中文方案名与版本号
FAIL 被改过的签名链接拿不到交付包（404）
FAIL 方案改版后旧交付链接失效（410）
```

根因：`JwtQueryGuard` 背后的 `JwtStrategy.validate` 要拿 payload 里的 `sub` **查库**
（`user.findUnique` + 比对 `tokenVersion`）。交付包链接是自签的，`sub='plan-package'`，
查不到用户 → `USER_NOT_FOUND` → 401。

正确语义是 **presigned URL：链接本身就是凭证**，靠 `JWT_SECRET` 签名防伪，
下载端不再查库、不再套 RBAC（生成链接时已经校验过 `content:generate`）。
能力清单里该端点声明为 `[]`，与无守卫的分享页一致。

> 教训：`JwtQueryGuard` 的适用面是「登录用户的资源」，
> 不是「任何需要 URL 直达的产物」。把二者混用会得到一个看似有鉴权、实则永远 401 的端点。

### 17.5 自己写的弱断言

同轮还发现一条自己写的坏断言：

```ts
check('下载到的是真 zip（PK 魔数）', (await dl.arrayBuffer()).byteLength > 0);
```

标签写着 PK 魔数，实际只判长度 > 0 —— **任何错误响应体都有长度**，
所以 4 个真实失败里有 1 个被误报成 PASS。改成真的比对 `buf[0]===0x50 && buf[1]===0x4b`。

断言的名字必须对应它实际检查的东西，否则下次排查时它会替你撒谎。

### 17.6 新增依赖

`jszip@3.10.2`（API 侧）。选型与合规核对：

- 依赖树里**已有**（pptxgenjs 间接依赖），不是新引入的陌生包
- 许可证 `(MIT OR GPL-3.0-or-later)` → 取 MIT 一支，符合项目要求
- `npm audit` 无 jszip 相关漏洞记录
- 备选 `archiver@5.0.0`（也在依赖树里）体积更大且面向流式场景，本场景用不上

### 17.7 只增不减的文件写入

交付包每次校对后重新打包都会在 `uploads/plan-packages/` 留一份。
按项目既有教训（「只增不减的文件写入要自己带保留策略」），`prune()` 每个方案只保留最近 3 份，

### 18.1 先查代码再决定做什么

## 二十、生产容器路径首次验证（0.2.2，2026-10-18）

### 20.1 一个一直没被验过的路径

用户要求「具备开源后给伙伴们部署」时才意识到：**从 0.1.83 到 0.2.1，
所有浏览器实测都跑在 vite dev 上，而 compose 里的 `web` 服务（Nginx 托管静态资源
+ 同源反代 `/api`）从未被真实验证过。**

vite dev 直连 api:3080，**不经过 nginx**。这意味着 nginx.conf 里的任何问题
在开发模式下都是隐形的。伙伴克隆下来 `docker compose up -d --build` 才会撞上。

### 20.2 撞上两个真实缺陷（都在容器部署下才暴露）

**缺陷一：交付包上传会被 413 拒。**
0.1.89 做的 `POST /api/plans/{id}/package` 后端限 60MB（`FileInterceptor`），
而 nginx `location /api/` 只给 `client_max_body_size 12m` ——
**超过 12MB 的方案包在生产部署下直接 413，而 dev 模式完全正常**。
实测确认 20MB 通过（旧配置应被拒）→ 修后 201。

**缺陷二：方案列表接口被 301 跳走。**
为修缺陷一新增 `location /api/plans/` 时踩到 nginx 的一个特性：
**带尾斜杠的前缀 location 会让 nginx 对 `/api/plans` 自动发 301 补斜杠**。
结果是 `GET /api/plans`（方案列表）跳到 `/api/plans/`，**生产部署下方案列表直接坏掉**。
改为 `location /api/plans`（不带尾斜杠）后恢复 200。

### 20.3 修法

```nginx
# 路径不能带尾斜杠，否则 /api/plans 被 301
location /api/plans {
    proxy_pass http://api:3080;
    client_max_body_size 64m;        # 后端 60MB + multipart 边界余量
    proxy_read_timeout 300s;         # 收 60MB + zip 压缩都要时间
    proxy_send_timeout 300s;
    proxy_request_buffering off;     # 一次性请求，缓冲只拖慢并占磁盘
}
```

普通上传的 `location /api/` 保持 12m 不动 —— 实测确认 20MB 走
`/api/media/uploads` 仍被拒，不会因为给交付包放宽就把所有上传的口子一起放开。

### 20.4 生产路径实测记录（web/api/db 三容器）

| 项 | 结果 |
|---|---|
| `GET /api/plans`（曾 301） | 200 |
| 3MB / 20MB 交付包上传 | 201 / 201 |
| 70MB 交付包上传 | 413（nginx 64m 先拦，符合预期） |
| 20MB 走普通上传 `/api/media/uploads` | 413（12m 仍生效） |
| 签名直链下载 | 200，20MB zip，PK 魔数，`Content-Disposition` 带中文名 |
| 篡改 token | 404 |
| 接口抽查（plans/media/team/products/orders/tokens/content/feedback/manifest） | 全部 200 |
| 首页 / 深链 `/quota` / 不存在的资源 | 200 / 200 / 404（SPA 回退与静态 404 都正确） |
| 浏览器登录 + 侧栏渲染 | 正常，15 项全出 |

### 20.5 补 smoke 断言（这类差异本地测不出来）

```
交付包路径的上传上限 >= 后端 FileInterceptor 的 60MB（生产环境否则 413；实测 64m）
交付包 location 不带尾斜杠（带尾斜杠会让 /api/plans 被 301 跳走）
普通上传路径上限独立生效且更小（实测 12m vs 交付包 64m）
```

> 写断言时踩了个小坑：第一版用 `\n  \}` 收尾 location 块，但文件里块结束是 4 空格缩进，
> 正则静默匹配不到 → 断言假失败。改为「从 location 声明切到下一个 location 声明」，
> 与缩进无关。**断言假失败比断言不写更糟** —— 它会让人以为配置真的有问题。

## 二十一、批次 6 落地：交付前预检闸门（0.2.3）

### 21.1 先划清范围：出图队列对我方是「新增能力」不是「补缺口」

批次 6 的原始定义是「出图队列 + 6 态状态机 + 仅补齐失败页 + 预检闸门」。
动手前核实我方现状：

```
apps/web/src/data/planThemes.ts
  pageImageType(type) → /images/cases/c1..c5.jpg   ← 5 张固定静态图
  sceneImage(subtitle) → 按关键词挑其中一张
apps/api/src/**  → 无任何逐页出图逻辑
```

**我方方案页配图是静态预设图，没有「逐页 AI 出图」这个流程。**
所以「出图队列 6 态状态机」对我方不是补缺口，而是**新增一条出图链路**，
它会改变成本模型（N 页 × 生图额度）与等待时间（逐页生成数分钟）。
这类产品决策不该由实现者替用户拍，故本版本只做**与出图无关的预检闸门**，
出图队列留在批次 6 剩余项并在下面写清取舍。

### 21.2 预检闸门：参考站 preflight-content 的我方实现

参考站 N13：`preflight-content`（`canGenerate` + `warnings[]`，app:3628/4128），
判定规则在服务端、前端只读结论。我方按同边界实现：

```
GET /api/plans/{id}/preflight          （content:read，只读不扣额度）
→ { canDeliver, pageCount, warnings: [{ index, heading, field, snippet }] }
```

查什么：逐页扫**内部待办语句**（「待确认」「暂无资料」「TBD」…）。
为什么不静默净化：净化会让人以为系统吃了内容；为什么不全量阻断：
门店有权决定改还是删，位置必须先报出来。所以是「点名 + 不拦」。

与前端 `lib/planSanitize.ts` 的分工：那边**净化**（生成客户版正文），
这边**报出位置**。两边同规则，`(?<!再)` 等刻意改进也必须同步。

### 21.3 差点又犯「误报」的错

smoke 第一版造了个「干净方案」，正文写「全部内容已确认，无待办事项。」——
**这句话本身含「待办事项」，被判成有问题**，断言 FAIL。

这不是测试数据写错，是**真实误报**：门店真写「本页无待办事项，全部已确认」
会被告知「第 1 页正文：有待办语句」，荒谬且会让门店不再信任这个功能。

修法（与净化侧同一类保护）：

```ts
// 「待办事项」「资料缺口」这类词本身要防否定
|(?<!无)(?<!没有)(?<!不含)(?:资料缺口|待办事项)
|(?<!无)(?<!没有)TBD
```

「没有待办事项」的前两字是「没有」，lookbehind 只看紧邻一个字符，必须单独排一次。
本地用 dist 产物跑了 12 例判定（含 5 个否定场景），全部符合预期后才进 smoke。

> 预检类功能的价值全在「不误报」。误报一次，用户就再也不看它了。

### 21.4 实测（生产容器）

| 项 | 结果 |
|---|---|
| 三个真实方案预检 | 全部 `canDeliver=true` / 零告警（模型生成的文案本身干净） |
| 造一条含内部语句的页（第 9 页） | `canDeliver=false`，精确报出「第 9 页 · 正文：主材价格待客户确认。」 |
| 交付页告警态 UI | 「第 1 处内部待办语句，打包交付前建议先处理」+ 逐条页号/字段/片段 |
| 交付页通过态 UI | 「交付前检查通过：11 页均无内部待办语句」 |
| 跨租户访问预检 | 404，不泄露他人方案内容 |

触发时机：点「进入交付」时自动查；保存单页文案后自动重查（结论可能已过时）。

### 21.5 出图队列的取舍（明确不做，理由写清）

参考站的 6 态（done/generating/partial/unknown/settlement_pending/interrupted）
是为「LLM 出文案 → 逐页出图 → 打包」这条链路设计的，我方目前没有中间那一步。
要做等于**新增一条出图链路**：逐页调生图模型、按页记录状态、失败页可单独重试、
前端队列与轮询。工作量大且直接改变成本模型。

本版本不做。等明确要做「AI 出图版方案」这个产品决策后再动，
届时状态机与「仅补齐失败页」要一起做 —— 单独做一个「批量出图」按钮，
失败后只能整份重跑，那才是真的不好用。

### 21.6 一个流程教训

改完 `PlanStudio.tsx` 后我只重建了 api 容器就去测 UI，**预检块完全没渲染**。
原因是 web 容器还在跑旧镜像 —— Docker 不会因为源码变了就重建。
排查花了一轮才定位。**改前端就必须 `docker compose build web` + `up -d --force-recreate web`**，
且改完要核对镜像 ID，否则测的是上一版的页面。

## 二十二、批次 10 落地：提交幂等全链路（0.2.4）

### 22.1 先盘点：我方幂等到底覆盖了多少

参考站 A9/A5 要求提交带 `clientRequestId` + digest，逐端点核对后，
我方全项目 8 个扣费点的覆盖情况是：

| 扣费点 | 幂等 | 说明 |
|---|---|---|
| 方案生成 | ✅ | PlanProject 带 clientRequestId |
| AI 生图 | ✅ | MediaAsset 带 |
| AI 生视频 | ✅ | MediaAsset 带 |
| 图片局部重绘 | ✅ | 同上 |
| 素材购买 | ✅ | 按 title 查重，重复购买不扣款（不同机制但效果等价） |
| **产品 AI 批量** | ❌ | 逐张生图，重试 = 整批再生 + 重复扣费 |
| **灯光问诊** | ❌ | 重试重复扣 |
| **接单 AI 接待** | ❌ | 重试重复扣 |
| **跟进建议** | ❌ | 重试重复扣 |

**5 处缺失。** 触发场景很常见：弱网超时后用户重试、跨标签页重复点、手抖连点。

### 22.2 为什么单独建一张幂等表，而不是给每张业务表加列

已有 `clientRequestId` 的表（MediaAsset / PlanProject）能「查业务表」直接返回既有产物，
比查幂等表更省事。但缺幂等的这几处没有可挂的业务行 ——
灯光问诊、产品 AI 批量的结果本来就不落成独立行。

给每张业务表都加一列意味着 4~5 张表各改一遍 schema、各写一遍抢占/释放/查结果，
而这套流程**完全一样**。所以抽成一张 `IdempotencyRecord`：

```
(tenantId, key) 唯一约束 + kind + result(JSON) + createdAt
```

### 22.3 关键设计：用唯一约束抢占，不是「先查后插」

「先查后插」在并发下会双双查到空、然后双双插入 —— **两个并发点击照样扣两次**。
所以 `claim()` 走的是直接 insert，靠唯一索引让第二个请求当场失败（P2002），
失败后再回查带回既有结果。这是并发防线的真身。

租户也在唯一键里：B 租户用与 A 相同的键互不影响（smoke 有断言）。

### 22.4 失败必须能重试

抢占成功后如果执行报错，必须 `release()` 删掉占位 ——
否则用户第一次失败后就再也提交不了了。

这里与参考站的处理**刻意不同**：参考站 app:4125 是「卡住时强制查原任务、
**禁止重新提交**」，那是给异步出图队列的（避免重复下单给供应商）。
同步端点失败应当允许重试，两者不能混为一谈。

### 22.5 向后兼容

`clientRequestId` 全部是可选的：不传就不参与幂等，行为与之前完全一致。
老调用方、Agent、curl 都不会被拦。

### 22.6 冒烟抓到一个联动缺口

加了新表之后，smoke 的「全库备份覆盖 schema 每一张表」直接 FAIL ——
`BACKUP_TABLES` 里没有 `idempotencyRecord`。

这条断言的价值就在这里：**它专治「加了新表忘了同步各处引用」**。
备份漏了它，恢复后重试窗口内的提交会被当成首次执行，可能重复扣费。
已在 `backup.controller.ts` 补上（备份与恢复共用同一张清单，补一处即可）。

### 22.7 前端四处同步

后端接了不等于生效 —— 前端不传键就等于没接：
`LightingDiagnosis`（问诊）、`OrderStudio`（接待解析 + 跟进建议）、`ProductCenter`（批量处理）。
做法与既有生图/方案一致：操作进行中保持同一个键，成功后清空（下次是新操作）。

### 22.8 新增断言

```
首次抢占成功（应当真正执行）
同键再次抢占被拒（重复提交不会重复执行）
不同租户用同一个键互不干扰（键按租户隔离）
完成后再次抢占仍被拒，且带回上次结果
释放后可以重新抢占（执行失败必须能重试）
不传 clientRequestId 时不参与幂等（向后兼容）
带幂等键调问诊：LLM 不可用时按原样报错而不是返回占位结果
幂等记录确实落库（可在租户维度追溯）
```

## 二十三、批次 8 落地：方案场景视频与分享页内联播放（0.2.5）

### 23.1 按「不过度开发」定下的范围

用户明确要求：**复刻不要过度开发，开源免费不需要在额度上折腾，模型都是客户自己的**。
据此把批次 8 收窄成一件事 —— **让分享页能放视频**。

### 23.2 刻意不做「在方案页现场生视频」

参考站方案页有「选择 AI 图片 / 生成视频」这类入口。我方**不做现场生成**：

- 模型是客户自备的（云端 API 或本地 ComfyUI），现场生成要**消耗客户额度**且慢
- 门店的真实路径本来就是：先在「AI 生视频」出好片 → 再挂进方案
- 复刻一个「现场生视频」按钮，等于把参考站的收费模型搬进免费项目

所以只做**绑定 + 播放**，现场生成留给独立的生视频工作台。

### 23.3 做了什么

| 位置 | 内容 |
|---|---|
| Prisma | `PlanProject.videoAssetIds String[]` + `videoTitles String[]`（同序） |
| `PATCH /api/plans/{id}/videos` | 绑定，最多 2 条（参考站同上限） |
| `GET /api/public/plans/{token}/video/{index}` | 免鉴权视频文件流，分享页直接 `<video src>` 播 |
| 交付页 | 「绑定场景视频」按钮 + 资料库多选弹层（只列 `kind=video && status=ready`） |
| 分享页 | 视频区块放在**幻灯片之前** |

### 23.4 分享页为什么把视频放在最前面

客户在微信里打开链接，**先看到「装出来是什么样」，再看逐页文案**。
放在末尾会被当成附加彩蛋而错过 —— 参考站的「全屏播放」也是把视频当主内容。

### 23.5 分享页是免鉴权端点，所以绑定必须逐条校验

绑定时对每条 id 校验三件事：**存在 / 属于本租户 / `kind==='video'` / `status==='ready'`**。
写错 id 就等于把别人的视频挂到公开页上，这是数据泄露而不是功能缺陷。

视频文件流用 `createReadStream().pipe(res)` 而不是整段读进内存 ——
视频体积大，整段 `readFile` 会把容器内存顶爆。

### 23.6 新增断言

```
把图片当视频绑定被拒（400，分享页不能挂错类型）
绑定他租户的视频被拒（400，不把别人的东西挂到公开页）
超过 2 条被拒（400，与参考站同上限）
合法视频绑定成功并返回 id 列表
分享页能读到绑定结果（分享视图据此内联播放）
越界的视频序号取不到（404，不会串到别的资产）
不存在的分享 token 取视频 404
```

### 23.7 smoke 抓到一个联动缺口

`byShareToken` 是**显式挑字段**返回的（不是整行返回，为了不把 `clientRequestId`、
`reviewedRevision` 之类内部字段暴露到免鉴权端点）。加 `videoAssetIds` 时漏了挑，
分享页就读不到绑定结果 —— smoke 的「分享页能读到绑定结果」当场 FAIL。

这正是白名单式返回的代价：安全，但**每次加字段都要记得同步**。
补上时仍保持白名单，没有改成整行返回。

## 二十四、方案编辑乐观锁（0.2.6）：堵住静默丢数据

### 24.1 问题：两个同事同时改方案，后保存的人会抹掉前一个人的修改

`pages` 在库里是**整份 JSON**，每次保存整份覆盖：

```
设计师甲打开方案（V4），改第 3 页 → 保存 → V5
设计师乙也打开方案（V4），改第 5 页 → 保存 → V6
```

乙提交的是「基于 V4 的整份 pages + 他对第 5 页的修改」，
**甲对第 3 页的修改被整份抹掉**，而 `versionNo` 照常从 5 涨到 6、
界面一切正常 —— 没有任何报错提示。这是**静默丢数据**，也是最难查的一类。

我方此前完全没有并发保护。

### 24.2 修法：乐观锁（带版本号保存）

客户端打开弹窗时记下 `versionNo`，保存时带上；服务端比对，不一致直接 409：

```ts
if (dto.versionNo !== undefined && dto.versionNo !== plan.versionNo) {
  throw new ConflictException({
    code: 'PLAN_VERSION_CONFLICT',
    message: `方案已被他人更新到 V${plan.versionNo}（你基于 V${dto.versionNo} 编辑），本次修改未保存`,
    currentVersionNo: plan.versionNo,
  });
}
```

`versionNo` 是可选的：不传就不检测，Agent / curl 等老调用方不会被拦。

### 24.3 与参考站的取舍

参考站的处理是 **409 冲突时落两份草稿快照到 localStorage**
（`p2_draft_{acct}:{proj}:conflict:{ts}`，app:3692/4182），让用户手动合并。

我方**不加草稿快照**，改为：409 带回服务端当前版本，前端提示
「方案已被他人更新，你本次的修改未保存，是否重新载入最新版本」，
并提供**重新载入**而不是**强制覆盖**。

理由：那份 pages 是整份 JSON，「强制覆盖」等于替对方做决定 ——
他可能也基于旧版改，改到最后谁都盖谁。重新载入至少保证
「丢得明明白白」而不是「不知不觉没了」，而且不需要在浏览器里存业务数据。

### 24.4 顺带改进：`api()` 的错误现在带 code 与 status

之前 `api()` 抛的 `Error` 只有 `message`，前端要判断错误类型只能匹配文案 ——
改一个字面量就静默失效。现在一并带出后端 `code` 与 HTTP `status`：

```ts
const err = new Error(body?.message ?? response.statusText) as Error & { code?: string; status?: number };
if (body?.code) err.code = body.code;
err.status = response.status;
```

这是全项目通用的 —— 之后任何端点抛 `ConflictException({ code })`，
前端都能精确判断，不用再猜文案。

### 24.5 新增断言

```
基于当前版本保存成功，版本号 +1
拿着旧版本号保存被拒（409，不静默覆盖他人修改）
冲突响应带明确错误码与当前版本号（前端可精确判断并提示）
A 的修改仍在（冲突那次没有写入）
B 的修改没有落库（那一页仍是原内容）
版本号没有因为失败的保存而增长
B 基于最新版本重试后成功（冲突不是死锁）
不传 versionNo 时不做冲突检测（向后兼容，Agent/curl 不受影响）
```

### 24.6 踩到的坑：乐观锁写了却不生效

第一版乐观锁**完全不生效** —— 409 从未触发，B 的修改照样落库，5 条断言 FAIL。

原因是 `updatePage` 的控制器**逐字段挑参数**传给 service：

```ts
return this.plans.updatePage(tenantId, id, {
  index: Number(index),
  heading: dto.heading,
  subtitle: dto.subtitle,
  ...
  quote: dto.quote,
  // ← versionNo 在这里漏了
});
```

我把 `versionNo` 加进了 zod schema 和 service 比对逻辑，却忘了在控制器里往下传，
于是 service 拿到的 `dto.versionNo` 恒为 `undefined`，比对分支永远不进。

这类「中间层漏传」最难发现 —— schema 有它、service 有它、断言有它，
**每一层单独看都像写对了**，只有跑起来才发现没接上。
已在控制器该行加注释标明这个坑，避免下次再改同一处时把它删掉。

## 二十六、核心链路首次端到端实测（0.2.8）

用户质询：「客户上传平面图后渲染高清装修图 → 放置/调节设备位置 → 融合进 PPT，
这整个都验证适配完成了吗？是否具备生产使用要求？」

**结论：之前没有验证过。** 本轮第一次把整条链路真跑一遍，撞出一个交付级缺陷。

### 26.1 五个环节的真实状态（实测，不是读代码猜的）

| 环节 | 实测结果 |
|---|---|
| A 客户上传/挂接平面图 | ✅ 真跑通（`PATCH /api/plans/{id}/floorplan` 200） |
| B 渲染高清风格装修图 | ✅ **首次真跑通**：22.3 秒出 1280×720 顶视精装图（此前所有版本的实测都没碰过它） |
| C **自动放置设备位置** | ❌ **我方没有这个能力**，点位全靠门店手点手拖 |
| D 手动调节设备位置 | ✅ 拖拽微调（`DeviceLayout.tsx:249`） |
| E 融合进 PPT | ⚠️ 代码有，但**点位被丢弃**（见 26.2） |

### 26.2 撞出的缺陷：有渲染图时，点位全部消失

两处同一病因：

```ts
// planPptx.ts —— 渲染图优先，点位合成被跳过
if (plan.renderedFloorplanUrl) { floorplan = 渲染图 }
if (!floorplan && plan.floorplanUrl && plan.layoutPoints?.length) { 合成点位 }  // ← 永不进入

// PlanSlide.tsx（分享页/预览）同样
const hasFloorplan = !useRendered && Boolean(plan.floorplanUrl && plan.layoutPoints?.length);
```

用户传平面图 → 配好设备点位 → 生成精装修图 → 交付物里那个
**叫「户型与设备点位」的页面上，一个设备都没有**。
这是「承诺了却不给」，不是「少个功能」——门店在该页上花的时间全部白费。

**修法**：底图与点位是两件事，不该二选一。底图取「精装修效果图优先」，
只要 `layoutPoints` 非空就往底图上叠：

```ts
const base = plan.renderedFloorplanUrl ?? plan.floorplanUrl;
if (base && plan.layoutPoints?.length) { 合成点位 → 裁剪 }
```

`PlanSlide` 与 `planPptx` 两侧同规则（前者注释里本就写了「两处各写一遍迟早只改一处」）。

### 26.3 修复前后对比（同一方案、同一份 PPTX）

| | `ppt/media/image-3-1.jpeg` | 画面 |

### 29.3 结论一：渲染模型不同，不是缺口

参考站 `floorplan-render` 是**多视角第一人称**模型：用户在户型图上摆
`camera（机位）+ lookAt（视线）+ region（目标房间矩形）`，
`rayIntersectsRegion` 用**射线-矩形相交**验证「这个机位真的看得见那个房间」，
最多 4 个视角，每个视角出一张图。

我方是**单张顶视风格化**：`render-floorplan` 生成一张
「风格化精装修顶视平面图（top-down floorplan render）」。

两者目的不同 —— 参考站给 3D 家装渲染用（站在客厅看客厅），我方给平面风格化用。
**照搬多视角等于成本 ×4**，且我方已实测 22 秒出一张，够用。判定：不追。

顺带确认一致的部分：`MAX_LIGHTING_SCENES = 3` 与我方毛坯房工作流的
「叠加智能灯光场景（最多 3 个）」**完全一致**，这部分 0.2.1 已经对齐。

### 29.4 结论二：可直接借鉴的是工程实践，本轮已落

参考站有 `MAX_POLL_FAILURES = 6`，`failureStatusText`，
说明它把「生成会失败」当常态在设计。我方此前：

- **先扣费后生成** —— 渲染一次 20~30 秒，失败就白扣额度
- **无重试、无超时** —— 一次网络抖动 = 一次失败 + 一次白扣

两个都是 2026 年生图服务的通行做法要补的：

**（1）新增 `common/retry.ts` 有限重试工具**，三条原则：
- 只重试「再试一次有可能成功」的错误（超时 / 连接重置 / 5xx / 429）；
  4xx 参数错与 key 无效重试多少次都一样，立刻抛出
- 有限次 + 指数退避 + 抖动（并发请求不会同毫秒一起重试）
- 最后一次抛**原始错误**，不用「重试失败」盖掉真实原因

**（2）扣费从「生成前」改为「生成后」**：
生成前只 `balance()` 预检余额（不够直接 403），生成成功才 `consume()`。
这样网络抖动重试 3 次全失败时，用户**一分钱没花**。

实测（本地 node）：网络抖动重试到成功 ✅ / 401 立即抛出不重试 ✅ /
5xx 重试到耗尽且抛原始原因 ✅ / 超时被兜住 ✅ / 默认 3 次不是无限重试 ✅

### 29.5 结论三：自动确认置信度（已有同类实践，未新增）

`AUTO_CONFIRM_CONFIDENCE = 0.85` + `geometryAutoConfirmEligible`
= 自动识别给置信度，高于阈值自动确认、低于则要人工确认。

### 30.5 踩到的坑：路径写错会伪装成「权限不足」
