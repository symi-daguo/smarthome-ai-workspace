### 1.6 页数核算公式（`app.js:3419-3434`）

- `floorplanCount` = 本地待传 + 已存

下限公式（app:3375-3379）：
```
residence-v1 : 8 + max(0, floorplanCount-1) + max(1, renderCount)
presales-v1  : 9 + max(0, floorplanCount-1) + renderCount
classic      : (!project || salesContentVersion===1) ? 10 + max(0, fp-1) + renderCount
                                                       : 3 + floorplanCount + renderCount
```

文案（app:3427-3433）：
- 公式段：`N 个沟通模块 + M 张额外户型图 + K 个素材展示页 = 至少 X 页`

### 2.1 页字段体系（`plan2-workspace.js` — 本次补抓）

**固定 7 个字段名**（行 3）：
```
['页型','主标题','副标题','画面要点','汇报要点','视觉建议','客户感知价值']
```

**页解析 `pages(text)`**（行 5-9）：按 `^## (Slide N|第 N 页)` 切分；
无匹配时整篇作为第 1 页；标题剥离前缀。

**字段解析 `fields(raw)`**（行 10-17）：
- 匹配 `^([^\n#：:]{1,48})[：:]([^\n]*)`（键 1–48 字，不含换行/井号/冒号）
- 去掉列表符号（`- * + • ·`、数字序号）与 `**`/`__`/反引号
- **边界字段** = 上述 7 个 + `备注/来源/补充说明/内部备注`
- 若当前 active 是「画面要点/汇报要点」且下一行不是边界字段，则**不切分**（即要点可以多行）

还有 `patchField(text, number, key, value)`：按页号+字段名做**局部文本替换**，
不重写整篇——这是「保存单页字段不破坏其他内容」的关键。

## 三、第 3 步：生成与校对（出图 + 逐页精修）

### 3.1 出图队列（`app.js:159-188`）

- **前端无并发池**，单请求长轮询；并发与批量全在服务端
- 轮询 **360 次 × 10s ≈ 60 分钟**
- 仅 `502/503/504` 静默重试，其他业务错误立即抛
- 超时抛 `backgroundGenerationNotice`，**不自动重做**，提示查历史
- 进度：`setP2(38 + done/total*55, '已完成 X / Y 页…')`（app:4129）
- 渐进式预览：已出页显示图、未出页占位（app:3973-3976）

### 3.2 状态机

`project.status`（app:3635/3356/4107）：`created` / `images-ready` / `packaged`

`imageJob.status` 6 态（app:4117-4120 文案表）：
| 值 | 含义 |
|---|---|
| `done` | 全部完成（**前端合成**：slides 存在且 status∈[images-ready,packaged] 时） |
| `generating` | 页面正在生成 |
| `partial` | 部分失败，可仅补齐失败页 |
| `unknown` | 供应商结果未确认，需查询原任务 |
| `settlement_pending` | 图片已返回，正在恢复保存与结算 |
| `interrupted` | 原任务已中断，已完成页保留 |

`textTask.status`：`queued/running/publishing/unknown`（app:4138）

**卡住时强制查原任务**（app:4125）：status ∈ {unknown, settlement_pending, interrupted, generating}
且非 resume → 直接走 `resumeP2Pending()`，**禁止重新提交**。

## 十、PPTX 导出实测结论（0.1.82）

### 10.1 已确认正常的部分

导出链路**其实是通的**，实测证据（浏览器 console + 落盘文件）：

```
[pptx] 开始导出，原始页数 9
[pptx] 待取图 4 张
[pptx] 原图取齐
[pptx] 裁剪完成
[pptx] 写文件…
[pptx] 字节数 952535
[pptx] 已触发下载 汉江一品 3 栋 1802-标准方案-V4-2026-10-16.pptx
```

落盘产物：`952535 字节` / **10 张幻灯片** / **10 个媒体文件**
（10 = 9 文案页 + 1 户型页 ⇒ **户型图页已进入 PPTX**，与分享页页数一致）

### 10.2 三个曾被误判为「不生成」的坑

| 坑 | 真实情况 |
|---|---|
| `pptx.writeFile()` | Node 端 API，浏览器里静默什么都不写。已改 `write({outputType:'arraybuffer'})` |
| Office MIME | `application/vnd.openxmlformats-…` 在 Electron 内嵌浏览器会被判为不安全类型。已改 `application/octet-stream`（下载行为由后缀名决定，与 MIME 无关） |
| **`a.download` 文件名** | **宿主行为，非前端缺陷**：`<a>` 是否 appendChild 到 DOM 都试过，Electron 下载时仍以 `.com.minimax.agent.cn.XXXXXX` 随机名落盘。`a.download` 是标准行为，**在正常浏览器里没问题**，只在本宿主内失效 |

### 10.3 结论与正解

`a.download` 失效属**宿主限制**，改前端绕不过去。参考站的正解已经逆向到：

- 服务端打包 `POST /api/projects/{id}/package` → 返回 `pptxUrl`
- 前端 `GET /api/projects/{id}/file-link?path=` → 换**真实 HTTP 签名直链**
- 用普通 `<a href="签名直链" download>` 触发

指向真实 HTTP URL 的下载不受 `a.download` 限制，且顺带满足「下载物与校对版本绑定」的架构要求（见第七节批次 9）。

**因此批次 0 与批次 9 应合并实施**：不再修浏览器端 blob 下载，改为服务端打包 + 签名直链。

### 11.5 实测发现并修掉的一个体验缺陷

首版用 `<InputNumber min={9} max={20}>`，实测输入 25 时 **AntD 会静默拦掉并退回 9**
（`onChange` 根本不触发，用户看不到任何提示，也不知道被拦了）。
参考站用的是原生 `<input type=number>` + 自行 clamp，行为是**可见的**。

改为 `parser`/`formatter` 允许任意数字进来，再在 `onChange` 里夹取：
输 25 → `onChange(25)` → 夹为 20 → 输入框立刻显示 20，用户看得见变化。

> 教训：能用组件内置约束时不要用 —— 但组件的约束如果是**静默**的，
> 对「用户知道自己输入被改了」的场景就是错的，必须自己夹。
