### 3.4 AI 画布消息整条丢失（本轮新发现）

发新 prompt 时前端**不传 `parentId`**，后端每条都建成**根轮次**；
而渲染侧 `headTurn = turns.find(t => t.parentId === null)` **只取第一个根**。

结果：第二轮出图成功、变体已落库（API 返回 201），**界面上整条消息不显示**。
smoke 全绿、typecheck 全过、数据层完全正确 —— 三道门禁全部看不出来。

- 发送时默认接在当前叶子之后（`parentId: baseTurnId ?? leafTurn?.id`）
- 渲染侧把所有根按时间串成一条线，兜住历史多根数据
- 修复后同一对话 4 轮全部显示，每轮都有独立的「再出一版 / 改这段描述 / 圈选重绘」

### 3.5 圈选重绘端到端验证（不再停留在「明确拒绝」）

本机无 OpenAI 生图 provider，此前只能验证到「准确拒绝」。本轮起 mock OpenAI 兼容端点，
把链路一路验到上游收到的字节：

- `POST /v1/images/edits` multipart 字段实测 `model, prompt, n, size, image, mask`
  （image 475B / mask 608B，尺寸均 256×171）

  涂选区外 = `{255}`，圈外 alpha=0 的像素数 = 0
  ⇒ **涂选处透明(=要重绘)、圈外不透明(=保留)，与 OpenAI 约定完全一致**

### 3.6 宽屏留白：根因不是列宽，是 flex 容器缺 grow

用户指出「界面留白太多挤在一起」。逐页量化后发现根因：

在 AntD `Layout` 的 flex 行里，一个**没有 `flex: 1`** 的 block 级 div 会退化成**内容宽度**——
两栏加起来多宽就多宽，剩下的全部变成右侧空白。实测报价页在 1920px 下右侧空出 **400px**（占内容区 25%）。

- `QuoteStudio` / `OrderStudio` / `DeviceLayout` / `PlanStudio`×2：主区容器补 `flex: 1` + `minWidth: 0`
  （`minWidth: 0` 是关键，否则 flex item 不会收缩到内容以下）
- 接单页 AntD 栅格 `lg={7}/lg={17}` 是**断点固定比例**，1920px 下左栏占 29%（约 472px），
  比参考站窄栏宽一倍 → 改为 flex：左栏 `0 1 300px`（上限 340）、右栏 `1 1 560px`
- 报价页产品库最终定 `0 1 380px`（上下限 340/420）：这是「名称+单价+SKU+规格」一行排得下的最小宽度。
  第一次收窄到 300px 时出现过「空调/伴侣」「智能摄/像头」断字，实测后回退

修复后实测：报价单区从「止于 1520px」变为「铺满到 1880px」，400px 留白消除，产品名称不再断字。

### 7.1 点位定位精度 —— ✅ 已实测准确，非问题

三处坐标系统一：编辑器点击按 `stageRef.getBoundingClientRect()` 归一化；
编辑器渲染按 `left/top: p.x|p.y × 100%`；导出合成按 `x = p.x * canvas.width`。
关键前提**实测成立**：舞台盒 `overflow:hidden` + `img width:100%` ⇒ 舞台盒与图片盒**完全重合**
（实测两者都是 2051×1154），归一化空间一致，不存在 objectFit 留边导致的偏移。

端到端实测（浏览器内拦截导出 blob，与底图求差分定位标记）：

| 项 | 期望 | 实测 | 差 |
|---|---|---|---|
| 点击落点归一化 | (0.25, 0.75) | (0.2496, 0.7498) | ~1px |
| 导出图标记圆左缘 | 0.2496 − 0.016 = 0.234 | 0.235 | 0.001 |
| 导出图标记 y 中心 | 0.7498 | 0.7475 | 0.002（≈2px，0.15%） |

（标记半径 r = canvas.width × 0.016，导出图 1600 宽时 r=25.6px。）
导出包围盒 x 中心偏到 0.291 是因为**名称标签向右延伸**（`lx = x + r + 6`），不是坐标偏移。

底图经「美化图纸」从 1024×576 放大到 2000×1125 后，点位仍停在 (0.2496, 0.7498) —— 归一化坐标不受尺寸变化影响，**已验证**。

### 7.3 产品图标 —— ⚠️ 确认存在缺口（本轮修）

实测与代码审查发现三处：

1. **24 个预置产品全部没有主图**。`seed.ts` 的 `PRODUCT_DEFS` **根本没有 `imageUrl` 字段**，
   接口实测 `有主图的产品: 0 / 24`。
2. 因此 `pointOverlay.compositePoints` 里「产品主图优先做点位图标（圆形裁剪），无图回退品类 SVG」
   这条**精心设计的路径是死代码** —— 注释写着「对齐参考站的产品图=点位图标」，实际永远走回退分支。
3. **同品类产品图标完全相同**：如「智能中枢网关」与「多模态网关」同为 `gateway`，都显示网络图标。
   39 个品类图标对应 24 个产品，同品类必然撞图标（网关 2 个、开关 3 个、灯光 4 个、窗帘 2 个…）。

缺的是**产品级图标**。修法：给 Product 加 `iconKey`，同品类内可区分；图标成为点位标记的主路径，

### 7.7 预览卡片排版复核（2026-10-15，用户指出参考站卡片更饱满）

**用户反馈**：参考站智能百宝箱的卡片「填满了每个卡片区域」，
「3 张海报」这类角标字样**在图片右下角很小的区域、没有超出卡片**；
而我方「差距很大、超出卡片区域、图片留白比较多」。

**根因（DOM 实测定位，不是目测）**：角标定位公式写成了
`right: calc(50% - ${CARD_W}px + 6px)`，其中 `CARD_W = 196` 是**写死的像素值**，
而卡片用的是 `gridTemplateColumns: repeat(auto-fill, minmax(300px, 1fr))`。两者一变位就错：

| 卡片内宽 | 角标 `right` 计算值 | 后果 |
|---|---|---|
| 320px | `160 - 196 + 6 = **-30px**` | **直接伸出卡片外** |
| 更宽 | 仍按 196 算 | 角标落在图片右侧的**空白区**里，与图片脱开 |

同时 196px 的图在 300px+ 的卡片里**只占约六成**，右侧大片空黑 —— 这就是用户说的「留白多」。

**改法**：`STACK_LAYERS` 的偏移与尺寸全部从 px 改成**百分比**，容器 `width:100%` + `aspectRatio:16/10`
+ `overflow:hidden`；角标锚在容器内的固定 `right:10 / bottom:10`，与卡片宽度彻底解耦。

**修后实测**（12 张卡）：
- 图片占卡片宽 **0.922**（改前约 0.6）
- 角标**在卡片内 = true**，距图片右 10px，尺寸 59×16（小而克制，与参考站一致）
- 旋转出界的层由容器 `overflow:hidden` 裁掉，不再外溢

**全站同款问题扫描**：写了扫描器遍历 12 个页面，找「有图元素宽度 < 卡片宽度 60%」（留白）
与「绝对定位子元素越出卡片且祖先没有 overflow:hidden 兜底」（溢出）。
第一版判据太松，把 14px 小图标也当成留白，产生大量假阳性；
收紧到「图宽 ≥60px 且高 ≥40px」后 **12 个页面零命中** —— 说明这是唯一一处真实缺陷。

> 工具选择说明：本来想写成一个可在门禁里跑的 playwright 脚本，
> 但项目没装 playwright —— 为一次排版检查引入一个浏览器依赖不划算（YAGNI），
> 改用已有浏览器跑同样的扫描逻辑，结论一样，不留新依赖。

```css
.space-card.locked .sc-soon { position:absolute; top:8px; right:8px; z-index:3; background:#ff8a00;
                             color:#fff; font-size:11px; font-weight:700; line-height:1;
                             padding:4px 9px; border-radius:11px; }
```

**核心就两条**：
1. **图片区自己定比例**（`aspect-ratio:16/10`）+ `width:100%` → 宽度永远跟着卡片走
2. **`object-fit:cover`** → 图裁切填满自己的盒子，绝不出现留白
3. 角标是**相对图片区绝对定位**的固定偏移（`top/right:8px`），不是相对某个写死的宽度算出来的

**DOM 实测**：参考站 18 张 `space-card` 里，**0 张带「张数」角标** ——
唯一的角标是 `.space-card.locked .sc-soon`（橙色「即将上线」标记，给未上线的卡片用）。
所以用户截图里的「3 张海报」是**我方自有的角标**，参考站并没有 —— 它是差异化点，不是要消除的对象。
**要消除的是「位置算法」**：我方角标用 `calc(50% - 196px + 6px)` 算，与卡片宽度脱钩。

**我方改法与参考站对齐**：容器 `width:100%` + `aspectRatio:16/10` + `overflow:hidden`，
图层改百分比定位（等效于 cover 填满），角标锚在容器内固定 `right:10/bottom:10`。
保留 3 层堆叠作为差异化（参考站是单图），但**填满卡片**这一点完全对齐。

### 7.14 已修：任务球固定 6 秒轮询（生产稳定性，非功能缺失）

用户要求「整体生产环境可以长期稳定运行」，按此标准复查任务投放行为，发现一处真实缺口。

**问题**（`components/TaskBall.tsx:75`，修改前）：
```ts
const timer = window.setInterval(() => void loadServerTasks(), 6000);
```
固定 6 秒、无视负载，且 `catch {}` 静默吞错（注释写「静默降级为纯前端任务」）。
配合后端 `canvas.service.ts:353` 的 `findMany({ where: { tenantId }, take: 50 })`
——**每次全量返回 50 行含 params JSON**，一天 14400 次／标签页，且以下情况照打不误：
无进行中任务、接口失败、token 失效、标签页隐藏。

**修法**（不引入依赖、不改后端、不动界面呈现）：
- 改为**自调度 setTimeout**（`setInterval` 在创建时就定死了间隔，无法自适应）
- 三档节奏：有进行中任务 5s / 空闲 60s / 失败退避 10s→300s 封顶
- `document.hidden` 时**完全不排程**；`visibilitychange` 切回前台立即补同步
- 失败时不清空 `serverTasks`，保留上一次结果，任务球不闪空

**口径**：`api()` 抛的 Error 不带状态码，所以**没做 401 熔断**——
那需要改全局 `lib/api.ts`，为单一用途动全局封装不划算；
通用失败退避已能把 401 场景压到 5 分钟一次，效果等价而风险更低。

### 7.18 【已修】遮罩约定的注释与 OpenAI 官方定义相反

`media.schemas.ts` 原注释：「**不透明区域会被重绘，透明区域保持原样**」。

查证 OpenAI 官方定义（四个独立来源一致）：
- `@openai/openai` TS SDK：`mask` — "An additional image whose **fully transparent areas (e.g. where alpha is zero) indicate where the image should be edited**"
- `openai-interface` Rust crate（镜像官方 schema）：同一句
- `openai` Ruby gem `ImageEditParams#mask`：同一句
- LiteLLM 文档："Mask image indicating **transparent areas to edit**"

即：**透明区域才是被重绘的区域**。`RegionSelector` 的实现（整幅不透明 → 把圈选处「擦」成透明）

### 7.19 【已修】存储治理：三个互相掩盖的根因（0.1.64）

用户要求排查「Mac 硬盘增大 + SSD 反复擦写」。查出三个根因，**每一个单看都不起眼，
合起来才造成 60GB 量级的浪费**。这也是本次最值得记的方法论。

#### 根因 1：`.dockerignore` 的 `uploads` 匹配不到嵌套路径

写的是 `uploads`，**只匹配仓库根目录那一个**，产物实际在 `apps/api/uploads`。
于是每次 `docker build` 都把 597MB 备份文件塞进构建上下文——
`COPY apps/api apps/api` 单层实测 **626MB**。

这才是"反复擦写"的主要来源：**每次编译都白读写 600MB**，
而磁盘占用只是表象。改为 `**/uploads` 后镜像 2.23GB → 1.62GB。

> 如果当时只看到「镜像占了 2.2GB」就去优化 Dockerfile，可能改了半天也省不下多少——
> 因为大头根本不是依赖，是被误装进来的业务数据。

#### 根因 2：API 镜像装了用不到的前端依赖

`pnpm install` 装整个 workspace，React + antd 进了 API 镜像。
`--filter @app/api...` 后再省 310MB。合计 **2.23GB → 1.31GB（-41%）**。

#### 根因 3：全库备份只写不删

`backup.controller.ts:54` 的注释是"留一份防下载中断"，但**没有任何保留策略**。
单份 20–23MB，从 10-08 堆到 10-15 共 **188 份 597MB**。

新增 `pruneBackups(dir, 3)`，**按 mtime 而非文件名排序**——
文件名里的时间戳来自 ISO 字符串，改时区或系统时钟就会乱序，
按名字删可能把最新那份当成最旧的删掉，那才是真事故。

**测试特意踩了这个坑**：造 4 份"文件名新、mtime 老"的假备份并用 `utimesSync` 把 mtime
压到 2001 年。如果实现按文件名排序，这 4 份假备份会活下来，**被删的反而是真备份**——
断言"被删的全是假备份、真备份一份没少"才能锁死这个方向。

#### 治理项

| 项 | 修改前 | 修改后 |
|---|---|---|
| 日志驱动 | `json-file`（**不加 options 时无上限**） | `local`（稀疏二进制，默认有上限） |
| db 容器轮转 | 漏配（靠驱动默认值兜底） | 与 api/web 统一 `10m × 2`，合计上限 60MB |
| `docker:prune` | `image prune -af --filter until=168h` | `image prune -f` + `builder prune -af --filter until=24h` |

**`image prune -af` 里的 `-a` 是危险的**：它会连**带 tag 的基础镜像**一起删。
本机 Docker Hub 超时（curl/ghcr 通、Docker Hub 不通），删掉 `pgvector/pgvector:pg18`
数据库就再也起不来。去掉 `-a` 后只清悬空镜像，基础镜像全部保留。

而 `until=168h` 太宽松：当天堆的 58 个悬空镜像（每个约 2GB）全被"保护"下来了，
等于没清理。改 24h 是"保留一天回滚能力"与"及时回收"的平衡点。

#### 数据完整性核对

清理前后逐表行数**完全一致**（User 721 / AuditLog 9545 / ChangeSnapshot 1698 /
MediaAsset 889 / TokenLedger 1684 …），数据库体积 32MB 未变。**无任何数据丢失或损坏。**

#### 未实施的两项（需用户决策）

1. **回收站仍有约 597MB**：本次删除走可恢复删除（环境规则），等于移动到回收站，
   同卷内并未真正释放。要真正回收需清空回收站。
2. **审计表无保留策略**：`ChangeSnapshot` / `AuditLog` 只增不减，
   开发环境每天新增 771–927 条（约 6.5KB/条）。
   门店正常生产每天几十次操作约 **118MB/年**，可控；
   但保留期属合规决策，**不擅自删除审计数据**。

### 7.24 【G-13 实施依据】参考站回复导出 MD/Word 的原文（REA + 源码复核，2026-10-16）

#### 原文（`app.js:1441-1482`）

```js
function contentToWordHtml(text) {
  const body = escapeHtml(text)                 // ← 先转义
    .replace(/^### (.*)$/gm, "<h3>$1</h3>")     // ← 再替换标签
    .replace(/^## (.*)$/gm,  "<h2>$1</h2>")
    .replace(/^# (.*)$/gm,   "<h1>$1</h1>")
    .replace(/\*\*(.+?)\*\*/g, "<b>$1</b>")
    .replaceAll("\n", "<br />");
  return `<html xmlns:o='urn:schemas-microsoft-com:office:office'
                xmlns:w='urn:schemas-microsoft-com:office:word'
                xmlns='http://www.w3.org/TR/REC-html40'>
            <head><meta charset='utf-8'></head>
            <body style="font-family:'PingFang SC','Microsoft YaHei',sans-serif;
                         font-size:14px;line-height:1.8;color:#222;">${body}</body></html>`;
}
// 下载（:1479-1482）
downloadBlob(content,                    `智能体内容-${fileStamp()}.md`,   "text/markdown;charset=utf-8");
downloadBlob("\ufeff" + contentToWordHtml(content), `智能体内容-${fileStamp()}.doc`, "application/msword");
```

#### 三个坑

1. **顺序：先转义再替换标签**。反过来就成了注入漏洞——
   模型返回的内容里带 `<script>` 时，先替换标签的话会被当成真 HTML 执行。
   实测 `**<b>x</b>**`：先转义后替换得到 `<b>&lt;b&gt;x&lt;/b&gt;</b>`（正确），
   先替换后转义会得到转义过的 `&lt;b&gt;` 实体被粗体规则吃掉。
2. **Word 文件必须带 BOM**（`"\ufeff"`）。不加 Word 按本地编码读，**中文全是乱码**。
3. **`xmlns:o` / `xmlns:w` 命名空间不能少**。少了 Word 只当成普通网页打开，排版全丢。

另外：复制要有降级路径（`navigator.clipboard` 不可用时退回 `execCommand`，
再失败才提示手动复制）；**操作条只挂 assistant 回复**（`app.js:1615` 的 `role === "assistant"` 判断）。
